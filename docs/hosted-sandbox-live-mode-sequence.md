## Recommendation

Build the hosted sandbox first, after a bounded investment in the shared wire and connection lifecycle. Develop live recording against those shared contracts, deliver browser-owned live execution next, and add hosted live execution only after proving how real credentials are provisioned, refreshed, isolated, and disposed.

Hosting and execution mode are independent choices. Hosting answers where the authoritative sandbox runs. Live mode answers whether a Firestore operation runs against the sandbox or real Firebase. A hosted sandbox does not require live mode; browser-owned live mode does not require a Node host.

Do not make the entire transport rewrite in ADR-0011 a prerequisite. Its characterization harness, lifecycle seam, side-split codec, and small capability handshake earn their place here. Its operation registry migration, generated manifests, file rearrangement, and full typed-call migration can wait.

## Execution method: TDD at agreed seams

Use the `tdd` skill for implementation. The landing sequence below describes dependencies and completion outcomes, not a horizontal schedule of writing all tests, then all infrastructure, then wiring the application. The gate catalog is an inventory of required behaviors. Implement its tests incrementally as each behavior becomes the next vertical slice.

The user explicitly approved S1–S6 and their documented scope in the active implementation goal; [the gate ledger](../GATES.md) records that agreement. The skill requires: “Test only at pre-agreed seams.” Reuse this approval throughout later cycles; ask again only for a materially different test interface or scope.

| Proposed seam | Caller-visible behavior tested there |
| --- | --- |
| S1 — application SDK | Normal public Firebase-shaped imports in the served app: values, auth/tenant behavior, listeners, errors, deletion, and selected execution target. Exercise real client/host implementations over the applicable transports. |
| S2 — bridge consumers | The consumer wire and published remote/MCP interfaces: admission, malformed-frame refusal, session ownership, reconnect, and cross-client behavior. |
| S3 — CLI host lifecycle | Start, stop, restart, and discovery through the CLI; verify persisted data by reconnecting and reading through the SDK. Inject filesystem failures at the filesystem seam, without querying private host maps. |
| S4 — live application execution | The app's instrumented SDK interface and actual external Firebase boundary: original results/errors/observer behavior, real identity, and no repeated upstream mutation. Use an isolated backend and real SDK objects. |
| S5 — observation consumers | The declared event/capture/replay interfaces and Studio: recorded context, uncertainty, loss reporting, retention, and explanations. A new observation interface must be agreed before testing it. |
| S6 — verification tools | A checker’s command-line input/output or documented callable interface: good/bad source fixtures, artifact reports, and gate completion failures. These test development tools rather than product implementation details. |

The exact scenario subset belongs in the confirmed seam record. Agree critical paths and complex failure cases; do not interpret the catalog as a requirement to test every helper or hypothetical edge case. Name tests with the vocabulary in CONTEXT.md and respect ADR-0011's public transport and cross-version contract distinctions.

For each new behavior or bug fix:

1. Select one behavior at one confirmed seam, with an independently derived expected outcome.
2. Write one test and run it. Record a relevant failing assertion before implementing the behavior. A missing dependency, crashed harness, or unrelated compile error is not red evidence.
3. Implement only enough production behavior to pass that test. Apply named local conditions and the code-quality rules while writing it; do not add extension points for future slices.
4. Run the test and the affected checks. Record green against the unchanged behavioral assertion and current implementation.
5. Review the green slice. Refactoring is a separate review-stage activity under this skill, not part of the red → green cycle. Keep it behavior-preserving, rerun the seam tests, and keep mechanical moves separate from behavior changes as required by the repo.
6. Select the next behavior. A subsection closes only when all of its required outcomes and integration gates pass.

Tests drive public interfaces with real internal collaborators. Doubles belong at external I/O, time, randomness, and transport fault injection, not at private helpers. A test must survive replacing internal maps, caches, or module layout. Do not assert internal collaborator calls or inspect private state to establish a public outcome. For the no-duplicate-write contract, observe the resulting mutation through the public SDK; external request tracing may corroborate that result. Resource checks use owned external handles or an agreed diagnostic interface, not test-only access to internal registries.

Existing-behavior characterization may pass immediately: record it as a baseline, not as a fabricated red → green cycle. Preserve those tests while reviewing refactors. Structural lint, typechecks, packaging audits, and sustained workload checks remain complementary gates; they do not replace the next behavior test.

The first hosted tracer bullet is “a browser writes through the normal SDK and a second browser observes that document from the same Node host.” The first live tracer bullet is “a normal app read uses the intended real SDK/App/Auth and returns its original result while recording one observation.” Extend these one behavior at a time with isolation, restart, and failure handling. Do not wait until every infrastructure section is complete before running either path.

This assessment serves the existing Refactoring and Tech Debt priority through demonstrated transport, persistence, and lifecycle coupling, and Trust through honest recording and execution contracts. The documents' proposed Hosted sandbox priority is still a proposal; this assessment does not edit PRIORITIES.md.

## Foundations and their scope

### 1. A wire value contract with explicit encoding

Keep a browser-safe value encoder separate from host-only decoding and write-transform resolution. Extend the existing leaf value codec instead of creating a second marker dialect. Reuse the shared sandbox foundation for cross-service identity, errors, and path handling.

Distinguish document values, write intent, and protocol envelopes. Optional envelope fields may be omitted deliberately; that is different from silently dropping a document field. Specify supported markers, reference project/database/path identity, transform descriptors, non-finite numeric values, and rejection behavior for cycles and unsupported values. Validate already-encoded messages on both MessagePort and WebSocket paths. Simply applying today's relay assertion to MessagePort does not achieve this.

Atomic writes must retain their storage intent through execution, request rules, and sibling `getAfter()` projections. A replacement `set` selects an update rule for an existing document, but must not acquire partial-update semantics along the way. The current replacement and merge/mask proofs cover batches and transactions over hosted and SharedWorker, including request rules, sibling projections and missing-field refusal.

Transaction execution now keeps its ordered queue instead of combining raw payloads. Shared preparation resolves each write against its predecessor's projected result; request rules and `getAfter()` use the final projection. The reviewed cases cover repeated masks and increments, nested-map replacement, and dotted updates that preserve siblings. An independent actual-SDK run against disposable Firebase emulators confirms final-document rules and ordered increments. Transaction diagnostics retain their existing one-result-per-path contract by summarizing after execution. The legacy exported reducer remains available to internal callers but no longer executes transactions.

Ordered storage preconditions now use each preceding projected state. Deletion followed by an update is rejected before mutation; deletion followed by set, with an optional update, is supported. Rules methods still use original existence and final projected state. These cases are verified through both write APIs and host transports.

Queued field masks, plain nested set/update values, and native Date values now retain their queue-time contents across hosted, SharedWorker, and in-page execution. Date transport uses the existing timestamp marker; in-page copying validates through the Timestamp factory and retains a detached Date for normal write conversion. Out-of-range Date inputs fail before entering a batch or transaction; the constructor checks nanoseconds before seconds, matching the SDK's error precedence.

Timestamp objects retain their original nanoseconds, while Firestore writes and query operands use microsecond precision. Shared write conversion applies that precision before rules evaluation and storage; query capture applies it to both comparison and execution. The wire codec retains the original representation. Independent real-SDK runs exposed two incorrect earlier fixture expectations about stored precision; those assertions now match the SDK. Equality queries also exposed skipped default ordering: the engine now always applies its existing normalized order, including the implicit document key. Four legacy ordering characterizations were corrected against the same SDK reference, as the separate correctness-fix path in ADR-0009 permits.

The modular transaction boundary now normalizes document snapshots through the same tagging and value helpers as ordinary reads. In-page transaction reads previously returned an Admin-style boolean `exists`; normal app calls to `snapshot.exists()` failed. Existing and missing documents now have browser proofs across all three execution paths. Reads remain inside the transaction's read-set tracking, and the legacy query-read overload is forwarded unchanged. A modular transaction adapter now preserves converted document models and callable existence checks; positive type fixtures exercise both published adapters without assertions. Converted snapshot references retain their converter for subsequent reads. In-page snapshots reconstruct stored references with their receiving SDK owner, and transaction reads use the shared document copier to preserve scalar types. Factory document references now retain their modular methods when a converter is removed and reapplied; the original reference remains unchanged. `setDoc`, batch set and transaction set have converted-model proofs across hosted, SharedWorker and in-page execution. The worker and modular atomic adapters convert before capture/encoding and rules evaluation. The modular batch now has explicit SDK reference types and forwards its existing commit options. Positive public fixtures compile these write paths without model index signatures or assertions. Other reference producers, converter options, full generic/overload constraints, exception timing and query/listener conversion remain required.

Both atomic adapters now validate root document shape after model conversion and before queue insertion. A caught invalid input leaves earlier accepted writes available to commit. The shared validator reuses the existing plain-object predicate and FirebaseError; its browser export does not import the engine. Thirty reviewed browser cases cover numeric, null, array and class roots plus numeric converter output, across batches, transactions and all three execution paths. Nested values, complete own-key fidelity and single-write/update validation remain open.

Wire path fields also need validation before reference construction. An array containing a document path previously coerced into a valid string and executed a write. The current setDoc and atomic descriptor paths reject that shape through the same shared host on WebSocket and MessagePort transports. Review consolidates batch/transaction write application and removes the transaction adapter cast. The six malformed-path cases verify refusal, absence of the rejected write, and continued shared-state access by both clients. Other path fields, complete envelope/payload schemas, admission, and size/depth limits remain required.

Atomic request validation also guards against partial success. An unknown descriptor method previously skipped that write while committing its valid sibling. An empty-string transaction read set bypassed read validation and committed both writes. Four red/green cycles now reject these shapes and return invalid-argument for null descriptors and non-array write lists. Two further cycles reject null read entries and array-valued read paths; the latter previously coerced its path and committed both writes. Four read-data cycles reject missing envelopes/JSON, malformed JSON and scalar document roots that were misreported as conflicts. Client read data is decoded and checked through the existing encoding and document-root validators before conflict comparison. The reviewed twenty-eight-case matrix covers both APIs and real transports where applicable, including unsupported read encodings. These checks do not establish complete nested-value schemas, qualified identity, descriptor options or resource bounds.

General composition remains open: other mutable inputs, own-key/class fidelity, pending single-write options, complete mask/transform validation, invalid/non-finite timestamp inputs, inbound frame validation, public adapter types, and event/capture/replay intent need further proofs. These specific passing cases do not establish arbitrary write-sequence correctness.

The current map-safe extension declares `valueEncoding: 'pyric/firestore-values/1'` outside document fields: on write and query-value descriptors and on serialized snapshot envelopes. Its encoder preserves scalar markers and wraps ordinary maps carrying `type`, `__type`, or `__type__` as `{ type: 'pyric/map/1.0', fields }`; fields are encoded recursively, including user maps that resemble this escape. Decoders interpret that escape only under the declared encoding and reject unknown encoding declarations. An absent declaration retains the legacy marker interpretation. The unary persistence decoder retains its existing contract until persistence has an explicit migration. This extension does not establish old-receiver compatibility: admission/negotiation, complete remote-writer adoption, and mixed-version refusal still need their gates.

Preserve the SDK's `getBlob()` return value by transferring encoded bytes and reconstructing a Blob client-side. Check `getDownloadURL()` too: the worker client currently builds it through `getBlob()`. Define size limits and errors without silently narrowing an existing MessagePort contract.

For live recording, encode a copy for events and capture. Forward the original SDK inputs and return the original snapshots on the direct browser path. Recording failures must not turn a successful real write into an apparent write failure that invites a duplicate retry. Surface recording gaps separately.

### 2. One connection lifecycle, with transport adapters

Separate temporary transport loss from explicit app deletion. Current `client/core.ts:disconnectPort` permanently marks the port deleted, rejects pending calls as app deletion, and removes listeners. It cannot be reused unchanged for reconnect.

Keep lifecycle ownership in one module: connecting, ready, interrupted, restoring, closed; pending calls; subscription intent; logical session identity; and generation checks for stale replies. On reconnect, establish protocol/configuration, restore tenant/auth/lens, then restore data listeners and allow queued initialization to proceed. Never automatically replay an uncertain write. Report that its outcome may be unknown if the connection dropped after execution but before acknowledgment.

The current hosted reconnect slice retains the logical SDK port and host identity using a private host-issued grant. An identity-protected Firestore listener now observes a change made while its socket is interrupted. The reviewed lost-ack case waits for reconnect and reads the committed increment through both the resumed app and another browser. An additional RTDB slice drains accepted onDisconnect work on socket loss instead of waiting for identity expiry; reconnect followed by deletion does not repeat that consumed work. These proofs do not establish complete tenant/lens restoration, stale-generation suppression, heartbeat and retention bounds, RTDB connectivity notifications, other service resubscription, or shutdown accounting. Those remain required before lifecycle integration is complete.

RTDB .info/connected listeners now combine the socket's observed attachment state with the app's explicit goOffline/goOnline choice. The browser review covers loss/recovery, another client's continued connectivity, explicit offline state surviving reconnect, both controls, unsubscribe/onlyOnce, and deleted-app refusal. Two further cycles fix parent .info snapshots remaining online and in-page listeners ignoring explicit network controls. The in-page adapter reuses its existing RtdbConnectionLifecycle, listener registry and app cleanup owner. Parent metadata, unsubscribe/onlyOnce and deleted-app refusal now have reviewed cases across hosted, SharedWorker and in-page execution. Constrained parent metadata now uses the existing query projection in both adapters. Four further cycles fix selected-field filtering, in-page connectivity propagation and unchanged-result suppression in each adapter. The twelve-case review covers selected connected values and iteration keys, unchanged serverTimeOffset, empty results and scoped off without canceling a parent listener, across all three runtimes. The pure projection and its types live in one internal leaf; the backend retains its existing exports. Two separately verified mechanical commits establish that boundary without duplicating the query algorithm. Scalar metadata queries and the remaining constraint/lifetime combinations still need direct proofs. Reset/import, complete host offline semantics, heartbeat and the other lifecycle requirements also remain open.

State replacement now cancels registered worker RTDB disconnect intent at the sandbox reset boundary shared by import, checkpoint restore and full reset. The hosted browser proofs wait for socket loss, resumption and acknowledged app deletion, then read through a fresh observer. Fresh registrations after import still execute. Import validation now rejects unrecognised bundles, missing or malformed metadata, unsupported v3 metadata versions, invalid service maps, malformed bucket/document maps and roots, and checksum mismatches before replacement. Recovery reads retain their existing corrupt-bucket quarantine. The shared connection handler returns validation errors on both transports; relying on the hosted shell alone previously left SharedWorker callers waiting. Complete raw legacy/schema validation, nested values, size limits and atomic all-service replacement remain required. RTDB data reset preserves deployed rules while clearing data and priorities, with allowed and denied reads checked after replacement. Already-running asynchronous work across reset, metadata refresh, explicit replacement scenarios in the other runtimes, and service-scoped reset still need proofs. Service CLI commands currently refuse a running serve and use the separate in-process store; hosted command/MCP attachment remains required.

Distinguish onValue with onlyOnce from get when testing metadata. An actual Firebase 12.13.0 SDK probe, taken offline before its first connection to an isolated local endpoint, delivers false for .info/connected and { connected: false } for .info through onValue/onlyOnce. Both get calls remain pending at the one-second observation deadline. The installed SDK routes metadata listeners through its local info tree but get through the ordinary server path. This is bounded disconnected evidence, not a claim about all connected get behavior. Do not implement a cached get result based on listener behavior; establish its separate upstream contract first. The sandbox's established serverTimeOffset of zero remains in its parent snapshots and is not claimed to reproduce pre-connection server metadata.

Add only the capability fields needed by actual callers: protocol compatibility, instance identity, retirement support, event-stream support, and persistence behavior. Preserve additive compatibility for separately released remote clients. Cover configuration and teardown frames as well as op/sub frames; the existing worker-op envelope alone is not the full `ClientPort` contract.

The hosted runtime now accepts the published remote consumer's operation and subscription relay alongside browser worker-port traffic. Both adapters use the same per-consumer queue and sandbox. Authenticated remote reads and listeners observe browser writes; separate remote auth sessions also work without a browser. Import review uses this published remote client instead of a handwritten control socket. This does not establish MCP tool dispatch, command attachment, every service family, durable authority or complete remote lifecycle. Unbounded remote event subscriptions fail explicitly while the required bounded observation relay remains unfinished.

Use the existing bridge consumer endpoint for browser sockets and an in-process peer adapter for the host. Avoid introducing a second socket protocol. In hosted mode, reserve the authoritative peer slot: today's last-connection-wins registration would let a browser peer replace the Node host. Hosted app pages must attach as consumers and must not auto-register competing worker peers.

### 3. A host runtime with explicit lifecycle and storage ownership

The session now declares whether the browser or host owns the legacy HTTP state channel. Hosted mode keeps state inspection available and refuses mirror writes before reading their bodies. A current-capability legacy client previously replaced a newer acknowledged SDK value on disk while running memory still showed it; restart exposed the older value. The SDK/restart proof now passes, and default SharedWorker persistence still hands saved data to a restarted host. This protects that server endpoint; process ownership and every other writer still need separate evidence.

SDK persistence admission now covers full reset, RTDB set/remove and Storage upload/delete in addition to Firestore. Storage acknowledgments flush the actual bytes and backend metadata through the existing state-file owner; restart proofs retain generations and timestamps. This exposed the distinction between a successful controller flush and complete service persistence. Explicit hosted flushes now share one queue: a delayed older Storage snapshot cannot replace a newer acknowledged value. A platform binary-I/O fault reproduced that loss through two SDK uploads and restart before the queue was added. A further reset race restored cleared objects because reset acknowledged before that queue drained. Full reset now uses the same persistence policy before acknowledging; an unhealthy host refuses reset before clearing memory. Default SharedWorker clear/reload/subsequent upload remains verified. Snapshot coherence during concurrent mutations, automatic controller flushes, reset generations, atomic multi-service commits, all buckets and remaining mutation families are still required before claiming authoritative durability.

Current persistence work uses the existing record bundle and atomic state store. SDK, MCP and service CLI acknowledgments have process-termination restore proofs; malformed envelopes and unsupported record versions refuse startup. SDK and MCP persistence errors now identify committed in-memory state, and a failed flush prevents further Firestore SDK mutations while reads remain available. All-service admission, health/recovery, other writer entry points, complete durable service/checkpoint/identity restoration, legacy import, backup accounting and interrupted commits remain required. These narrow proofs do not complete the storage owner or its durability contract.

The service CLI now uses declared method effects to check persistence health before durable mutations and flush their returned results, including unsuccessful results that may contain partial changes. Reads remain available with an explicit unhealthy-memory notice, and rules refusals retain their original result. The existing `switch_auth_identity` operation changes the CLI surface's held identity without writing persisted data; it remains available during disk failures and still controls subsequent reads. Complete service/control classification, other partial-failure paths and recovery remain required.

MCP tool-family records now declare each tool's read/write effect beside its name, preserving advertised names, factory order and metadata. The Node host skips persistence for reads and refuses declared mutations once persistence is unhealthy. Successful MCP and CLI reads share the in-memory-health notice. A returned MCP failure may contain partial changes, so it still triggers a flush; if that flush fails, the host preserves the original result and receipt and appends uncertainty guidance. Four public MCP red/green cycles and a partial-import characterization cover these paths. The service CLI shares this result-flush policy. Its sequential Firestore batch retains the missing-document error alongside the disk-failure notice; review proves partial changes survive immediate termination with healthy persistence and subsequent mutations refuse after failed persistence. Complete effect classification, other partial failures, all-service durability and recovery remain open.

Stdio MCP discovery now carries both the canonical directory containing the selected pointer and the discovered host instance on every HTTP request. The endpoint checks them before creating or resuming a session. Copied pointers and replacement between discovery and initialization have recorded assertion failures and unchanged green proofs. Valid subdirectory, symlink and Unicode workspace-to-frontend discovery have characterization coverage. These headers verify discovery context, not client authentication: direct endpoint clients retain the existing Host/Origin policy, and complete admission and cross-version refusal still need their gates.

Stdio request failure also needs an honest execution outcome. A dropped acknowledgment and a response that remains pending through the real 35-second deadline both previously told the caller to retry after a successful add. Both paths now report that the outcome is unknown, a write may have committed, and host state should be checked before issuing another write. Real CLI/HTTP fault tests read exactly one resulting document through normal browser SDK imports. The relay still does not replay requests. This covers those two failure paths; complete request classification, late-response handling and resource bounds remain required.

Extract only the ambient work that actually differs into injected dependencies: initialization data, persistence, capture sink, rules-change subscription, and diagnostics. The SharedWorker adapter can retain HTTP/SSE; the Node adapter can invoke the same underlying project modules directly. A fake fetch facade over relative URLs is acceptable for a spike, not the lasting interface.

Return a disposable host runtime containing the context and asynchronous shutdown. Today `buildWorkerCtx` discards several cleanup functions returned by init/hot-reload setup, and the event fan-out subscription is lifetime-long. That was tolerable when worker termination reclaimed everything; a restartable Node host needs explicit ownership of timers, event listeners, ports, persistence, and eventually upstream sessions.

Implement file persistence before presenting hosted mode as durable. Reuse atomic replacement and existing record codecs, but decide one authoritative writer, restore-before-seed ordering, corruption recovery, concurrent flush serialization, and flush failure reporting. `bestEffortFlush` currently logs failures and still returns success: document a memory-only success or introduce an explicit persistence failure state rather than claiming every acknowledgment is durable.

Storage bytes/metadata, auth users, RTDB, Firestore, checkpoints, and instance identity need a declared durability matrix. One storage owner need not mean one physical file. Keep legacy format import separate and avoid switching SharedWorker persistence unnecessarily. Credentials must not enter snapshots or capture files.

### 4. An observation model before a live recorder becomes evidence

The spike already distinguishes unknown prior state from an observed missing document. Extend that distinction through events, shadow state, capture, replay, and explanations.

Concrete issues in the spike justify this work:

- `recorder.ts:nextStateFor` and `shadow-store.ts:applyWrite` estimate updates with a top-level object spread. That cannot establish the resulting state of dotted updates, transforms, or selective merges. `writes.ts` classifies only `merge: true`, losing `mergeFields` semantics in the record.
- `reads.ts` classifies any successful snapshot as allowed without recording cache/server origin. The snapshot interface omits cache and pending-write metadata. A cached answer is not evidence that the backend just allowed a request.
- The recorder reads auth when recording the completed operation. An identity switch during an awaited request can attribute it to the next user. Capture request identity at issuance, and keep listener identity/generation explicit.
- `listeners.ts` counts every retained query document as modified and labels every stream error `permission-denied`. Preserve actual errors and use trustworthy change information or label counts as estimates.
- `explain.ts` evaluates against the current shadow and rules. Even a fully observed shadow may be stale or differ from deployed rules. No missing documents is insufficient to claim a complete explanation of the original denial.

Store operation identity, target project/database, observation time, source, relevant snapshot metadata, rules provenance, and completeness. Keep observed state, inferred write intent, and unknown state distinct. Do not add hidden reads merely to fill gaps. A local explanation should expose its assumptions and disagreement with the backend.

In hosted live mode, scope private observations to the relevant connection/identity and label privileged Studio aggregation explicitly. A shared event stream does not justify exposing one user's observed data to another app session, or presenting observations from different moments as an authoritative database snapshot.

### 5. Real upstream identity is its own seam

An emulated session, tenant, or admin lens is not a real Firebase credential. Preserve this distinction in types and lifecycle ownership.

Browser live mode should execute through the app's own authenticated Firebase handle and send encoded observations to the shared host. The worker receives observations, not credentials; it cannot execute with a page-owned SDK handle simply because HostCtx gains an `upstream` field.

Hosted live mode needs a credential-backed upstream factory scoped to a logical consumer, project/database, tenant, and credential generation. Prove real SDK initialization, reference/query construction from wire descriptors, token refresh, and listener teardown. The spike's wrapper only forwards functions over caller-created real references; it supplies none of those hosted mechanics.

Dispose old resources on sign-out, tenant/claims changes, port cleanup, and host shutdown; suppress callbacks from obsolete generations. Do not mechanically copy `sessionDbs.clear()`: those sandbox handles are cheap, while upstream handles own network listeners and credentials.

Carry the existing explicit production-write policy into live targets and agent operations. Do not silently substitute privileged backend identity for a missing user credential. Keep non-loopback hosting a separate release decision: allowed Host/Origin checks are not client authentication, and the current consumer protocol accepts client-supplied session identifiers. Decide admission, session ownership, and privileged Studio access before enabling credential-bearing LAN use.

These operator contexts are distinct and their complete identity/control parity still requires review. A copied pointer from another project now fails before mutation. The existing SharedWorker CLI refusal and explicit `--in-process` selection remain supported. Accepted tool/method work joins the host's shutdown wait, but complete scheduling, admission, resource bounds, service parity and durable acknowledgment remain required.

The hosted CLI now acquires project ownership before startup reads or resets state. A SQLite write reservation supplies the process lock through Node's or Bun's built-in driver, with no additional package dependency. The ownership file stays in place across shutdown; closing the connection or terminating its process releases the reservation. Review exposed two concrete traps: the initial native addon crashed Bun, and `BEGIN EXCLUSIVE` let simultaneous starters both refuse. The implementation uses `BEGIN IMMEDIATE`; the separate ownership evidence covers those corrections. This is a prerequisite for an authoritative store, not persistence itself, and other writer entry points still need the same ownership contract. CLI browser persistence and Vite persistence now acquire the same lock before state access or fresh reset. Real-process/SDK tests cover both startup orders and Vite failure/restart cleanup. Vite constructs its replacement before closing the old server, so teardown is bound to each server's own generation rather than the globally active generation. In-process MCP now holds the same reservation for its selected project until shutdown, including automatic fallback after missing discovery. One-shot in-process service commands reserve the load/execute/save sequence. Their runtime and snapshot/sidecar formats remain separate; shared runtime reuse, adoption/migration and the complete writer inventory still require implementation and verification.

Keep SharedWorker as the default until hosted mode proves itself in a release. Flag spelling is a small implementation decision; default-host migration, credential provisioning, durability guarantees, and non-loopback admission are the consequential decisions.
