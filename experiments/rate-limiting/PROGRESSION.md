# Firestore Rate Limiting

**The core scenario:** A shared AI gateway must enforce each user's allowance, withstand bursts, and limit expensive inference across multiple servers—even when requests disconnect, servers crash, or outcomes become uncertain.

Each technique adds protection that the previous one leaves missing:

1. **Transactional allowance accounting** ([inference-allowance/](inference-allowance/README.md), [first hosted comparison](inference-allowance/comparisons/first-hosted/README.md)): Without transactions, 50 concurrent requests against a 5-credit balance all succeed—the naïve read-then-write sees the same balance in every request. A Firestore transaction serializes the debit: 5 admitted, 45 denied, each producing a UID-scoped receipt bound to the request payload. On hosted Firestore the accounting stayed correct, but a 50-request burst caused enough transaction contention that every request timed out at the gateway deadline while debits silently committed in the background. Correct accounting does not bound the work spent checking it.

2. **Admission concurrency control and load shedding** ([progression](inference-allowance/EXPERIMENT-PROGRESSION.md), [hosted execution comparison](inference-allowance/comparisons/hosted-execution/README.md)): Two in-memory gates protect two different resources. A per-UID limit (e.g. max 2 pending admissions) stops one user from flooding the database. A per-instance limit (e.g. max 16) stops the container itself from drowning in concurrent transactions. Requests that exceed either gate get an immediate 503 without touching Firestore—Alice's 50-request burst drops from 116 transaction attempts to 17, while Bob and Carol complete all 6 of theirs uncontested. If a client disconnects or times out, the admission slot stays occupied until the underlying transaction actually settles, preventing retry storms. But the admission slot releases as soon as the database work finishes, before inference begins—slow provider calls accumulate downstream unchecked.

3. **Inference execution concurrency control** ([inference concurrency](inference-allowance/comparisons/inference-concurrency/README.md), [hosted execution](inference-allowance/comparisons/hosted-execution/README.md)): A separate reservation covers the full provider call—admission through settlement. Under admission-only control, 6 slow provider calls ran concurrently against a limit of 2; with execution reservations, exactly 2 ran and 4 were rejected before touching Firestore. The slot is not released when the client disconnects or the gateway returns a timeout—it is released when the provider actually finishes. On Cloud Run this matters: the HTTP/1.1 proxy does not forward client socket closures to the container, so the gateway never receives a disconnect signal, but the execution guard keeps the system safe because it is tied to provider settlement, not transport. The gap: process-local reservations cannot enforce a shared limit across multiple Cloud Run instances, and they vanish when a container crashes.

4. **Provider lifecycle accounting** ([lifecycle guide](inference-allowance/PROVIDER-LIFECYCLE.md), [local findings](inference-allowance/comparisons/provider-lifecycle/README.md)): The provider adapter separates two promises: `result` resolves when the output stream to the client ends, `termination` resolves when the provider actually stops. These are not the same event. The unsafe control released the slot 0.12 ms after transport failure while the remote provider ran to 902 ms—peak same-user concurrency reached 2 against a limit of 1. The safe version holds the slot until `termination` resolves, and when the provider's outcome cannot be determined—cancellation ignored, network partition, crash—the slot is quarantined indefinitely rather than released. This trades availability for safety: a quarantined slot blocks new work for that user, but never admits more inference than the system can handle. The gap: quarantine lives in process-local memory and vanishes when the container dies.

5. **Distributed capacity and recovery coordination** ([local harness](distributed-capacity/README.md), [hosted findings](distributed-capacity/hosted/RESULTS.md)): Reservations move from process memory to a shared Firestore document with `active` counts, per-owner lease deadlines, and a monotonic integer `fence` on each request record. 16 simultaneous requests across 3 gateway processes admitted exactly 3 (global limit) and rejected 13. Killing a gateway with SIGKILL left its reservation in Firestore—the slot stayed occupied. A second gateway took over the expired lease, incremented the fence from 1 to 2, and dispatched once. When the original gateway restarted, its operations were rejected because its fence was stale. The unsafe negative control released capacity on lease expiry alone and let 2 provider jobs run against a limit of 1. Hosted: 9 adapted cases across 3 Cloud Run PIDs, 46 checks, all passed. Gap: takeover and reconciliation were explicitly scripted by the test harness—no automatic recovery, and the provider fixture cooperated cleanly rather than behaving like a real AI API.

6. **Real-provider contract validation** ([local + live results](provider-contract/RESULTS.md), [live run](provider-contract/live/RESULTS.md)): Three evidence classes were tested against Firebase AI Logic (`gemini-3.5-flash-lite`). Completed response: the SDK returned `finishReason`, `usageMetadata`, and token counts—capacity was released. Client-interrupted stream: no cancellation API, no status query endpoint, no operation ID to poll—the outcome remained permanently unknown and the reservation was retained. Timeout or network failure: same result, no observable signal. 16 local fixture cases (35 checks) validated the evidence classifier and the safe/unsafe controls; 4 live cases confirmed the real API's behavior. The finding: Firebase AI Logic provides authoritative evidence for normal completions but exposes no post-interruption contract, so interrupted reservations cannot be safely released without external evidence that the provider stopped.

The remaining progression is documented as build briefs ([integrated-admission/](integrated-admission/README.md), [automatic-recovery/](automatic-recovery/README.md), [fair-allocation/](fair-allocation/README.md)) with implementation requirements but no code yet:

7. **Integrated admission and accounting** ([build brief](integrated-admission/README.md)): Combine allowance debits, capacity reservations, and dispatch decisions into a single Firestore transaction that produces an idempotent receipt. Test what happens when the process crashes between the debit and the dispatch, between the dispatch and the provider call, and between the provider response and the capacity release—without assuming exactly-once provider execution. Pre-dispatch cancellations refund both allowance and capacity atomically; post-dispatch outcomes release capacity but never refund allowance.

8. **Automatic recovery** ([build brief](automatic-recovery/README.md)): An autonomous worker scans for reservations with expired leases, takes ownership via fenced transactions, and settles based on available evidence. Reservations with confirmed provider completion are released. Reservations with no observable provider outcome are quarantined with an explicit reason rather than silently freed—the worker does not assume that a missing response means the provider stopped. The negative control releases capacity on lease expiry alone and proves the resulting concurrency violation.

9. **Fair allocation under contention** ([build brief](fair-allocation/README.md)): Three allocation policies—immediate rejection, bounded FIFO queue, and per-user round-robin—are compared under identical workloads, limits, and fake-provider durations. Measures whether a noisy user monopolizes shared capacity even when all accounting and concurrency limits are correct, and whether the Firestore coordination ledger itself becomes the bottleneck under high contention.

**Where to start:** Experiments 1–6 have runnable harnesses, captured evidence, and local/hosted findings you can reproduce against a Pyric sandbox or a real Firestore backend. Each experiment directory contains its own README with setup, execution commands, and links to result artifacts. The [common implementation contract](README.md) in this directory covers the shared capture format, CLI commands (`run`, `preflight`, `verify`, `analyze`), execution rules, and hosted deployment boundaries. Experiments 7–9 have detailed build briefs specifying case registries, failure injection points, and assessment criteria—everything needed to implement them—but no running code yet. Start with [inference-allowance/](inference-allowance/README.md) to see the full pattern, then follow the chain.
