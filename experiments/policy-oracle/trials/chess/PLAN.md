# Arcade chess conformance campaign

Deliver one playable Arcade chess match lifecycle authored in Pyric, from creating a lobby through a rematch. Ship a packed language implementation, an importable chess rules module, a resource-independent chess policy, and an oracle that future implementations can run offline. Publish exactly which requirements the deployed Firestore rules enforce. The unit of acceptance is the game.

## Freeze two contracts

David identifies Arcade as the only implementation of chess in Firebase Security Rules known to him. Preserve its original sources, dependency revisions, linked ruleset digest, client behavior and hosted receipts as a versioned reference.

* **Arcade storage compatibility.** Pin Arcade at `66e14d4f4b0aeab22c05db8d748704dde053d2e5`. Cover the five exports in `games/chess/chess.rules`, the enclosing match in `app/firestore.modules.rules`, the imported turn-net helpers, and both paths used for rematches. Record what the unmodified release allows and stores. The generated compatibility module must reproduce those observations, including cases where a client subsequently flags a move.
* **Arcade chess legality.** For a prior position and a proposed move, derive legality, the entire successor position, and the outcome. Use Arcade's `games/chess/src/chess.ts` and `logic.ts` as the shipped reference. Cross-check legal moves against a separately pinned orthodox chess engine such as Stockfish. Keep board legality, Arcade's document encoding and hosted access decisions as distinct expectations. Record a disagreement between references as disputed with a minimal position and both results.
* **Scope.** Include every shipped match action and every outcome Arcade implements. The native engine adjudicates checkmate and stalemate. Clocks, repetition claims, move-count draws and dead-position adjudication would require a separate product profile. Keep a full-strength enforcement build separate from the stock-compatible build so each has an unambiguous contract.

## Run it as a campaign

1. **Freeze and dispatch.** The supervisor publishes the position, move, match and verdict formats, stable claim IDs and source pins. The independent verifier retains a hidden corpus and its digest outside author worktrees before candidate scoring. From that interface, start protocol, chess semantics and verification in parallel. Capture stock outcomes while the policy is being written. A compiler owner can begin linking the stock module immediately. Parallel work packages can queue to fit available capacity.
2. **Integrate continuously.** Run the first complete match as soon as ordinary moves are available. Bring each subsequent work package into that same consumer. Share immutable test positions and public expectations. Give each claim its own `suites/arcade/chess/claims/<claim>/v1/` subtree, each compiler change a single owner and each production release one capture controller. Discover records by directory. Only the supervisor freezes a combined baseline.
3. **Climb against the public oracle.** On every candidate revision, run the previous baseline, all chess claims and deliberately altered implementations. Report false accepts, false refusals, mismatched fields, surviving mutations and the first divergence with its position, move, turn and field. A new receipt for an existing answer does not increase coverage. A pending or disputed obligation remains in the denominator. Keep the hidden suite for locked submissions and add a fresh holdout after publishing a former hidden case.
4. **Qualify the deployment.** The controller deploys stock, generated compatibility and the stronger candidate in turn to the isolated live Firestore database, retaining the release and linked artifact digests. Use the normal SDK under the intended identity. Also exercise unauthenticated read controls. For each database-dependent requirement, predeclare an applicable positive and negative case, or document which side the operation admits. Take server reads before and after every write attempt. Verify the entire successor on acceptance and unchanged state or absence on refusal, including all documents in a batch. Retain raw receipts outside the candidate tree and verify them with the oracle. Use the SDK's actual verdict and distinguish it from the requirement name assigned by a controlled case. Restore and verify the prior release.
5. **Resolve enforcement placement.** Firestore allows 1,000 evaluated expressions per request and zero recursive calls. Try the expensive checks in the complete linked game. Record static bounds, hosted results and unresolved limits separately. If any legality check stays standalone, demonstrate authoritative admission by evaluating it against the current stored match in a version-checked transaction, with direct client writes unable to skip that check. Race two submissions against the same prior state. Show the successful transition and the refused attempt's readback. A client replay provides an additional diagnostic. [Firestore Rules quotas](https://firebase.google.com/docs/firestore/quotas#security_rules)

## Release gates

* **Game semantics.** Publish exact root move lists and branch counts for the opening through depth four and at least four named special or tactical positions through depth three. A branch count is the number of legal continuations under a particular opening move. Cross-check independently. The Arcade engine's opening totals measured during planning were 20, 400, 8,902 and 197,281. Keep every named edge case above plus a reproducible set of at least 64 seeded match traces, with seeds and stopping conditions frozen before implementation. Include scripted complete games to each shipped terminal outcome. [Stockfish's reference position suite](https://github.com/official-stockfish/Stockfish/blob/master/tests/perft.sh)
* **Test sensitivity.** The verifier must detect independently introduced defects in turn or count, sliding movement, castling rights, en passant expiry, promotion, self-check, terminal result and atomic rematch. Require the first differing move or field. A matching final board or an aggregate move count alone cannot pass this gate.
* **Deployment.** Every scoped requirement has an owner, authority, artifact and evidence. Label the demonstrated layer for each requirement as hosted Firestore, authoritative standalone admission, or both. Mark unresolved and disputed items explicitly. Require zero unexpected hosted decisions, state mismatches or unresolved mandatory obligations before claiming completion. Claim Firestore-only enforcement only when the whole-game artifact meets that gate on its own.
* **Reproduction.** From a clean install, generate the modules, link the complete Arcade rules, run Pyric without Firebase, replay stock and candidate receipts offline, and repeat two-client Chromium play against the qualified deployment. Archive tool versions, policies, rules digests, first-divergence output and the capability report. Keep all existing oracle baselines green. Report progress by closed obligations, and keep working across package boundaries until the game passes or a reproducible blocker identifies what remains.
