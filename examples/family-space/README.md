# Kin — a little closer

A private family workspace built with **React, TypeScript, Vite, and the Firebase SDK**, running locally through Pyric. The Parker family shares photos, videos, articles, and events; parents choose what appears in the family feed and each kid’s personal feed.

## Run

From the repository root:

```sh
bun install
bash scripts/build.sh
bun run --cwd examples/family-space dev
```

Open **http://127.0.0.1:5227/**. This port is strict so another example cannot silently replace it. The Pyric runtime chip is injected by the Vite plugin; the app itself uses normal `firebase/*` imports. A full repository build also makes Studio available at `/__pyric/ui/`.

The app starts signed out. Expand **Try the example family** on the sign-in page to fill an account, then choose **Send sign-in link**. Pyric opens a local email preview; choose **Open sign-in link** to finish in a new tab. Keep the requesting tab open until sign-in completes so the temporary local worker retains the pending link. No password is required and no external email is sent locally.

| Account | Role |
| --- | --- |
| `emma@kin.example` | Parent |
| `daniel@kin.example` | Parent |
| `sam@kin.example` | Kid |
| `zoe@kin.example` | Kid |

The seed also includes `alex@kin.example`, a member of a different family, for testing denied access. These are fictional local accounts. No production users or personal account data are included.

## Try the family flow

1. Sign in as Sam. Create an article and choose **Send for review**. It appears in **My posts**, awaiting approval.
2. Sign out and sign in as Emma. Open **Parent review**, inspect the post, choose Everyone or a kid, then **Approve & publish**.
3. Sign in as the selected kid. Read the post and add a comment. Opening a published post records that kid’s view.
4. Return as Emma. The post detail shows who viewed it. Change the audience to move it between the family and kid feeds.
5. Edit the approved post as its kid author. It returns to review and disappears from published feeds until approved again.
6. Open Schedule and switch between Day, Week, and Month. Events use the same authorized posts and open their full detail.
7. Open Chat. Send a message, attach a photo/video/audio file, or use **Voice** to record and send up to a minute of audio.

The chip exposes the normal authentication, listeners, requests, and Storage activity generated by these flows. Use its user switcher for development inspection, or the app’s ordinary sign-out/email-link flow.

## Permissions and data

Membership is stored at `families/{family}/members/{uid}`; the `role` in that document determines parent access. Kids cannot grant themselves parent rights.

- Parents curate audiences and approve or decline posts. They can moderate family content.
- Kids create pending posts. They may edit or delete their own posts and comments, but cannot edit another person’s content or choose a post’s audience.
- Editing an approved kid post sets it back to pending; keeping it published is rejected by rules.
- Published posts are readable only by their family or selected recipients, plus parents and the author. Pending and declined posts are visible only to parents and their author.
- Only a kid may write their own view record, using a server timestamp. Parents can list view records; other kids cannot.
- Chat is shared only with family members. Message authorship is immutable.
- Uploaded media uses authenticated Storage reads. Post attachments follow the post’s audience. Kids cannot overwrite approved attachments without returning the post to review.

The narrow feed queries are intentionally separate: published family posts, published posts for the signed-in kid, and the kid’s own posts. The client merges their results. Queries are not used as a substitute for rules enforcement.

`firestore.rules` and `storage.rules` enforce these boundaries. `firestore.indexes.json` supplies the feed index. `seed.json` supplies fictional auth users and initial Firestore content. Seed photos and the sample video are public demo assets; user uploads are stored under protected Storage paths.

## Attachments and local persistence

Photo, video, and audio uploads must be smaller than 25 MB. Browser recording requires microphone permission and a secure context: localhost or HTTPS. On another device, use HTTPS (for example Tailscale Serve); ordinary HTTP to a LAN address cannot record microphone audio. Audio file attachment remains available.

Pyric’s SharedWorker keeps local sandbox state shared across tabs using the same origin. This example does not provide a production backend, family invitations, or cross-device synchronization. Different browser profiles/origins have separate local sandboxes. Use Pyric’s persistence tools to export work you want to keep; the committed seed remains deterministic.

## Separate port / remote access

Set `FAMILY_PORT` to change the local port. For a separate HTTPS Tailscale proxy on port 8458, start with:

```sh
FAMILY_REMOTE_HOST=your-device.your-tailnet.ts.net \
FAMILY_REMOTE_PORT=8458 bun run --cwd examples/family-space dev
```

Then point that HTTPS proxy at `http://127.0.0.1:5227`. This example does not change an existing Tailscale Serve configuration or occupy Orbit’s port.

Design sources and media attribution are recorded in [ASSETS.md](ASSETS.md).

Email-link completion remembers the requesting email on this browser. If the link is opened elsewhere, the app asks for the email again; it never trusts an address from the URL. Invalid or used links offer a new-link action. In a real Firebase project, enable Email Link authentication and authorize the app’s domain.

### Family apps

Open **Apps** in the side or bottom navigation. Parents can describe a small React app, select its recipients, preview a private draft, and then share it. Generation uses the standard Firebase AI Logic SDK; Pyric reads AI settings from an ignored `.env.local`. For live Gemini, set `PYRIC_AI_MODE=production` and `GEMINI_API_KEY`. For local Ollama, use `PYRIC_AI_MODE=sandbox` and `PYRIC_AI_MODEL=ornith:9b`. Restart Vite after changing these settings. Live generation sends the selected context to the configured provider; Firestore, Auth, and Storage remain sandboxed.

The context snapshot includes family member names/roles, up to 40 published posts visible to every selected kid, the events in those posts, and the latest 40 shared chat messages. It excludes pending posts and media bytes. Changing the audience or refreshing context requires generating a new version so an existing private snapshot cannot silently be shared more widely.

Generated apps import `useAppData` from `@kin/app`. It returns live `records`, `loading`, `error`, `setRecord(id, object)`, and `deleteRecord(id)`. Records live at `families/{family}/apps/{appId}/records/{recordId}`. All members of that family can read and edit these records; outsiders and signed-out users cannot. App source/context remain private to the creator until shared with selected recipients. Discarding an app removes its listing but retains its records.

The preview uses the filesystem and React compiler from `@inbrowser/workspace`. Compilation happens in the host; generated JavaScript runs only inside an opaque-origin sandboxed iframe with a restricted CSP. A scoped message bridge performs Firestore operations using the current signed-in identity. The iframe receives no Firebase credentials, arbitrary collection access, or direct networking. Apps inherit Kin's stylesheet and font pairing. They can interact with their own records, but cannot alter the family feed, schedule, or chat.

Run `node test/apps.mjs` for the deterministic preview/persistence check and `node test/apps-live.mjs` for a real configured-provider generation check (it sends the selected family context to that provider). Run `bun test test` for permissions and recipient-context tests.

Generation uses a host-controlled, checkpointed workflow in a named SharedWorker with `@inbrowser/resumable`. The model authors a permission plan, policy source, independent permission cases, UI selection and React source. Kin runs resolution, linting, policy parity tests, compilation and an isolated startup check; the model cannot skip those gates or declare success.

Firestore is the recovery source of truth. Each build has immutable, hashed checkpoints containing its frozen inputs, workspace files, policy evidence, selected references and attempt budgets. UTF-8 chunks stay below 256 KiB. A fenced transaction advances the checkpoint pointer only after uploads complete. A 60-second executor lease, renewed every 20 seconds, prevents competing tabs or devices from committing the same build. The local IndexedDB event log remains a delivery cache, not the only copy of the work.

A model connection or response that sends no progress for 90 seconds pauses with a saved diagnostic and an explicit Resume action. Stop interrupts pending connection and stream waits. Draft autosave coalesces queued keystrokes, and editing a candidate restores its version metadata even before activation.

Closing a tab does not stop a healthy worker when another authenticated tab can persist its progress. If no eligible tab remains, the next persistence or startup boundary interrupts work. A terminated worker is discovered on the next signed-in visit, including without its old local job ID. Kin offers **Resume**; it does not automatically issue another model request. Completed stages are restored, while interrupted HTTP requests restart. Builds do not run while the browser is shut down. Sign-out invalidates the executor and preview session.

Policy, compilation and startup validation allow two automatic repairs. Planning and UI selection allow one schema correction. Counters survive reload; **Retry stage** starts an explicit new attempt group for that stage. **Start over from draft** retains the original prompt. Startup checks require the isolated preview's ready handshake within 15 seconds and a further two seconds without runtime errors. They do not prove every interactive behavior.

A ready result is an immutable app-version candidate, saved only after validation and a Firestore acknowledgement. Activation, sharing, rollback and existing records retain their existing safeguards. Checkpoints and activity are owner-only and retained until permanent app deletion. Git and OPFS persistence are not used.

Run `bun run test:generation` for worker termination, Firestore discovery without a local pointer, explicit Resume and candidate persistence. `bun test test/build-checkpoints.test.ts test/build-workflow.test.ts` exercises the repository against Pyric's sandbox and the host stages against a deterministic model. `node test/authored-policy-browser.mjs` covers generated policy activation and runtime enforcement. The legacy provider smoke scripts continue to exercise the original producer independently.

### Starter templates

The Apps page includes ten working starters. Seven mix practical tasks with family fun: **Dinner Spinner**, **Chore Quest**, **Weekend Picker**, **Pack & Go**, **Kindness Jar**, **Reading Trail**, and **Family Time Capsule**. Three focus on play: **Story Relay**, **Connect Four**, and **Family Trivia**. The games use shared records and honor-system participant selection; they do not provide competitive turn locking or authenticate the player chosen inside a game.

A parent chooses a template and its recipients, with only that parent selected by default. Creating it saves a private app copy; preview it and explicitly share when ready. Each copy has its own Firestore records under its app ID, using the same family-member access rules as generated apps. Editing a copy does not change the template. Opening a starter does not invoke the model.

Catalog prompts live in `templates/catalog.json`; reviewed React sources and generation evidence live in `templates/generated/`. These starters were generated through the resumable AI workflow, UI-kit search/coverage/retrieval tools, and workspace compiler, then reviewed and corrected. Authoring uses only synthetic family context. Template source is not currently supplied to the in-browser generation agent as reference material.

From this example directory, with the server running:

```sh
# Generate missing sources using the configured AI provider; existing sources are skipped.
node scripts/generate-templates.mjs
# After reviewing/editing sources, update both installation outputs.
node scripts/seed-templates.mjs
# Exercise copies, primary interactions, reload persistence, and mobile overflow.
node test/templates.mjs
```

Set `KIN_BASE_URL` to use another server origin and `TEMPLATE_ID` to author or test one catalog entry. Generation makes real provider requests; the template browser check does not.

The seed writes templates to `families/parkers/appTemplates/{id}`. Existing sandboxes install missing template documents from `/app-templates.json` when a parent opens Apps; existing documents are not overwritten. Both payloads come from the same seeding script. Rules allow family reads and parent creation, and deny template updates/deletes.


### App health and recovery

Opening a generated app checks that its React preview mounts successfully. Sharing is disabled until this startup check passes. Render errors and unhandled runtime failures show **Try again**; the parent who owns the app also sees **Repair app**. Repair sends the existing source and error report through the resumable generation flow, compiles the replacement, and updates only the source of the same app. Existing records and sharing settings are preserved. Concurrent source changes stop the repair from overwriting a newer version.

This is a startup check, not a guarantee that every interaction works. Try the repaired preview before sharing. Repair uses the configured AI provider and the app's original context. Run `bun run test:recovery` for a synthetic browser check covering failure, retry, repair, saved data, and reload without a live model request.

`generation-instructions.md` is the system instruction used directly by both page and durable-worker model calls via `generation-model.ts`. It describes the configured Kin preview, not every capability the workspace library could optionally support. ### Firestore UI kit

The canonical copy-and-adapt examples live at `families/parkers/uiKits/kin-v1/entries/{id}` in Firestore. `seed.json` includes seven versioned entries; `scripts/seed-ui-kit.py` is their authoring utility. Run that script after editing reference source to regenerate the seed. Parents can read and create entries; updates and deletes are denied. Publish a new kit ID for revisions and update the loader deliberately. No OPFS or bundled runtime fallback is used.

`ui-kit.ts` implements the browser-local `searchUi`, `readUi`, and `checkUiPlan` tools. Search uses descriptive metadata and tags. Read expands dependencies and rejects unknown IDs and cycles. Coverage is a lexical aid, not proof that a design is appropriate. Unmatched requirements are explicitly reported as gaps.

Before starting a new build, the authenticated page loads and validates the Firestore kit. The SharedWorker asks the model for a small JSON needs/selection plan using catalog metadata only. It executes search, coverage and source retrieval locally, fills uncovered matches with the highest-ranked suggestion, and sends only selected patterns and dependencies as reference source for code generation. These helpers are copied into App.tsx, not imported as packages. This is a structured planning phase with host-executed tools, not a native provider function-calling agent loop.

The full Firestore snapshot is read once per build for this small initial kit. The model does not receive all source. The workflow checkpoints retain the exact kit snapshot and selected source in Firestore, so worker recovery does not change versions. Selection and tool evidence appear in App activity; resumed builds reuse completed selection. Future optimization can split metadata/source reads without changing the tool contracts.

Verification: `bun test test/ui-kit.test.ts`, `bun test test/permissions.test.ts`, `node test/ui-kit-browser.mjs`, and `node test/resumable.mjs`. The browser checks use a simulated model. A live provider generation with family context is not needed to verify retrieval or reference rendering.

Existing browser sandboxes can predate the UI kit seed. `loadUiKit` now runs an idempotent Firestore migration: if required entries are missing, it fetches the static deployment payload at `/ui-kit/kin-v1.json`, creates only absent documents in a transaction, and rereads Firestore. This payload contains only UI reference code and metadata, never family data. It is generated alongside `seed.json` by the same authoring script. It is installation data, not a runtime catalog fallback; complete Firestore kits do not fetch it. Existing kit entries and all family/app records remain untouched. Corrupt existing entries produce an explicit error instead of being overwritten. Regression coverage uses Pyric sandbox APIs (`test/ui-kit-upgrade.test.ts`) and the real browser worker bridge (`test/ui-kit-browser.mjs`).

## App drafts and versions

Parents' prompts autosave to `apps/{appId}/drafts/main`. The editor also keeps a
per-user recovery copy on the device until Firestore acknowledges the save.
Conflicting edits from another tab require explicit recovery instead of silently
replacing the saved draft.

An app keeps its ID and `records` collection across regenerations. Each build
freezes its input and records diagnostics in `builds/{buildId}/events`. Successful
builds create immutable `versions/{versionId}` metadata and separate `source` and
`context` artifacts. The app document retains the active source/context projection
for existing clients and shared recipients; history and build diagnostics are
owner-only. Existing apps are captured as Version 1 when their owner opens them.

Use **Edit app → Generate version** to build a candidate. Candidate previews use
a temporary in-memory copy of records; **Use this version** changes the active
version without replacing live records. Switching to an older version does not
roll back data. Generation instructions require backward-compatible record
schemas; automatic destructive data migrations are not supported.

Failed or stopped attempts return to an editable saved draft. Retrying starts a
new attempt and retains the old diagnostics. **Delete app** moves it to Trash;
restore keeps it private. Permanent deletion removes drafts, versions, artifacts,
build logs, and records before deleting the app document.

Verification: `node test/app-lifecycle.mjs`, `node test/app-draft-conflict.mjs`,
`node test/resumable.mjs`, and `node test/recovery.mjs` use the real browser and
Pyric sandbox with a deterministic model fixture. `bun test test` covers the
sandbox permission boundaries and generation producer behavior.

### Chore Quest app policies

Chore Quest templates expose live identity through `useAppIdentity()` from
`@kin/app`: `{user, loading}`, where `user` contains `uid`, `name`, `avatarUrl`,
`familyId`, and `role`, or is null while unavailable. Identity changes dispose
of the preview session and its subscriptions and pending requests.

The host evaluates the pinned Chore Quest policy with `pyric/rules` before
writes. A Firestore transaction reads the active version, membership documents
and target record, evaluates the proposed operation, and writes only on ALLOW.
Parents manage chores; kids can toggle only their assigned chore's completion.
All family members retain shared record reads. The deployed family-membership
rules remain the backend boundary: these local policies do not secure against
a modified family client bypassing Kin.

Policies are immutable version artifacts alongside source/context. Validation
records the resolved-policy hash, library/engine contract versions, a fixed
permission matrix, standalone evaluation results and seeded-sandbox results.
Activation rejects unsupported policies, incompatible existing records, and
policyless versions of an already protected app. Isolated previews evaluate
candidate policies but write only to temporary records. Offline policy writes
are rejected, not queued. Policy failures expose a code and diagnostic details
in the preview; app code receives a rejected data-operation promise.

The pinned `chore-quest-v1` policy and authored format-2 policies are supported.
Private record queries, batches and automatic schema migration remain unsupported. Ordinary legacy apps remain policyless. To upgrade
an existing Chore Quest, create a new version with the updated template source
and policy artifact, validate its existing records, then activate it; never
replace historical source artifacts or reset records.

Run `bun test test/app-policy.test.ts` for the public rules/sandbox checks and
`node test/policy-browser.mjs` for identity, direct bridge denials, concurrency,
isolated previews, offline errors and version failures.

### Policy-aware generation

New builds use separate host-controlled permission planning, policy source, and permission-case stages before UI selection and React generation.
The host provides capability declarations, retrieves pinned Firestore Rules Standard Library modules,
resolves `2+modules` source, and runs evaluator plus sandbox checks.
Permission cases are authored from the agreed contract independently of policy source.
Stage results, permission assumptions, and evidence appear in App activity.
The legacy producer and its smoke scripts retain the earlier bounded policy-planning tool loop.

Generated apps can use the pinned Chore Quest contract or an authored contract.
They receive live-identity instructions, the selected source and permission cases,
and a policy-bearing version with validation evidence.
Regeneration and repair retain the policy, including for an unactivated candidate.
The host validates again before saving new-workflow policy artifacts and before activation;
existing-record compatibility is checked at activation. Isolated previews use temporary data.

Other requests can explicitly select family-trust behavior (no extra app-specific policy).
Requests beyond the runtime capability boundary stop with an unsupported message.
Do not describe family-trust builds as policy-validated. Local policies do not secure
Firebase against a modified client.

Run `bun run test:generated-policies` against the running local sandbox. The optional
`bun run test:generated-policies-live` uses the configured model with synthetic family data
and checks policy planning and React compilation without saving an app. It may incur model
usage. Standard tests use deterministic model responses and real sandbox operations.

The module resolver/catalog currently use Pyric's existing browser tooling entry point
`pyric/rules/internal`; policy decisions and sandbox tests use public APIs. Keep this
adapter pinned alongside the host until a public resolver/catalog facade is available.

#### Authored policy boundary

`app_policy_prepare({source, summary, cases})` accepts modular Firestore rules for
the exact nested app-record match documented by `app_policy_capabilities`.
The host parses the resolved rules through the public rules API, rejects other
match scopes and unsupported dependency paths, and re-resolves persisted source
to check artifact integrity. Membership dependencies may reference the current
UID or top-level fields in before/after records. The transaction reads those
members and the record afresh on every retry. Authored writes replace records;
the pinned Chore Quest parent merge behavior remains unchanged.

Agent cases use fixed host fixtures (two parents, two kids, outsider and signed
out); the agent cannot supply auth claims or mocked dependencies. Every operation
needs a denial case and the suite needs a successful write. Host-owned mutations
test outsider and signed-out requests, including outsider-owned records.
Both evaluator and sandbox must agree with all expectations. Failed tool results
retain explanations for repair. Evidence is tied to the resolved policy hash,
fixture revision, engine/library identifiers and recorded cases.

Passing checks is bounded evidence, not proof that the agent captured every
product requirement. Existing-record compatibility requires at least one current
member to be able to create the same data or perform a no-op update. This conservative
check may reject immutable historical records; it never migrates them automatically.
Policies requiring cross-record state, getAfter, private reads or batches are rejected.

Run `bun test test/authored-policy.test.ts` and
`node test/authored-policy-browser.mjs` for authored ownership, hostile cases,
version persistence and direct bridge enforcement.

The optional `bun run test:authored-policies-live` runs the real configured provider
with synthetic note-ownership requirements and never saves or activates an app.


Policy preparation supports source-first authoring: call
`app_policy_prepare({source, summary})`, then `app_policy_cases({cases})` in
small batches (`mode: "append"` for later batches), and finally
`app_policy_test({})`. Incomplete case batches cannot become a selected policy.
Absent create-before/delete-after documents accept either omission or JSON null.
Invalid cases report their array index and field. These tool APIs remain available for the legacy producer and standalone validation. New builds use explicit host stages instead of a model-directed tool loop.

Draft regression checks: `node test/draft-autosave-regression.mjs` covers typing over delayed worker transport; `node test/draft-edit-regression.mjs` covers first creation, candidate metadata, and stopping/restarting a stalled edit. Both use local fixture responses.

Saved-version loading regression: `node test/app-version-loading.mjs` checks navigation between apps, missing-source diagnostics, and retry after artifact recovery using synthetic sandbox records.
