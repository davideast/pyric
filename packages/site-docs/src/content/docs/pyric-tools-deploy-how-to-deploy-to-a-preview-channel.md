# How to deploy to a Hosting preview channel

This guide shows you how to deploy a site to a temporary preview URL instead of the live channel. It's the same model as `firebase hosting:channel:deploy`.

## What a preview channel is

Every Hosting site has a `live` channel (what `<siteId>.web.app` serves) plus any number of named preview channels. Each preview channel gets its own server-assigned URL:

```
https://<siteId>--<channelId>-<hash>.web.app
```

The `<hash>` is generated by Hosting. It comes back on the channel resource's `url` field and cannot be predicted locally. Channels auto-delete at their `expireTime` (default TTL: 7 days, maximum 30 days). Deleting or expiring a channel never touches live.

## From the CLI

```sh
# Named channel
pyric deploy hosting --channel pr-417

# Branch-derived channel id (preview-branches sugar)
pyric deploy hosting --channel auto

# Custom lifetime: 30m, 12h, or up-to-30d
pyric deploy hosting --channel pr-417 --channel-ttl 12h

# Mirror form (the firebase-tools spelling) — identical behavior:
pyric hosting:channel:deploy pr-417 --expires 12h
```

`--expires` is an alias of `--channel-ttl` and works on either spelling.

On success the CLI prints the preview URL and its expiry:

```
Hosting deploy ok — 12/12 files uploaded; preview at https://my-site--pr-417-8a31bc0e.web.app (expires 2026-06-17T00:00:00Z)
```

`--channel auto` derives the id from the current git branch, sanitized to Hosting's constraints: lowercased, every character outside `[a-z0-9-]` becomes `-`, dash runs collapse, trimmed to 63 chars, leading/trailing dashes stripped (`Feat/Auth_Resolver.P4` → `feat-auth-resolver-p4`). A detached HEAD has no branch name. Pass an explicit `--channel <id>` there.

## From the programmatic API

```ts
import { hosting } from 'pyric-tools/deploy';

const result = await hosting.deployFiles(scope, {
  siteId: 'my-site',
  localDir: './public',
  channelId: 'pr-417',
  channelTtl: '43200s', // optional; protobuf Duration. Default '604800s' (7d).
});

if (result.success) {
  console.log(`Preview: ${result.data.channelUrl}`);
  console.log(`Expires: ${result.data.channelExpireTime}`);
}
```

`channelUrl` and `channelExpireTime` are read from the channel resource the Hosting API returns, never synthesized.

## Channel lifecycle

- **First deploy creates the channel.** The deploy ensures the channel exists (`POST …/channels?channelId=…` with the TTL) before uploading anything, so an invalid channel id fails fast with `CHANNEL_FAILED` and zero uploads.
- **Re-deploying to the same channel reuses it.** The create's 409 ALREADY_EXISTS is treated as success and the existing channel's URL stays stable. Your PR link doesn't change between pushes. The existing channel's TTL is **not** extended (`channelTtl` applies on creation only; extending an existing channel's TTL is deferred).
- **Expiry deletes the channel, not the versions.** After `expireTime` the preview URL stops serving. Deploying to the same channel id again creates a fresh channel (new hash, new URL).
- **`live` is another channel.** Passing `channelId: 'live'` (or omitting it) releases to the live channel via the original release path. Existing callers see byte-for-byte identical behavior. Releasing through `channels/live/releases` would be equivalent on the wire; the omit-path is kept for stability.

## Versions vs channels

A channel deploy still creates a normal, finalized version under the site; only the **release** step targets `…/channels/{channelId}/releases` instead of the site's live releases. That means content-hash dedup works across channels: a preview deploy of mostly-unchanged files uploads almost nothing.
